# heroesreplay CLI

Entry: `src/HeroesReplay.CLI`. Assembly name `heroesreplay`. System.CommandLine 2 (`Subcommands`, `SetAction`). No command needs administrator rights except `client firewall`. `spectate` runs unelevated (issue #133): launching Battle.net and HeroesSwitcher, PrintWindow capture, OCR, the memory clock, and hotkeys all work at normal integrity. Only adding Windows Firewall rules needs an elevated shell. Invalid input is a parse error and exits 1 before anything runs.

```powershell
dotnet run --project src/HeroesReplay.CLI --no-launch-profile -- <command>
```

`--no-launch-profile` is required; launchSettings would otherwise inject leftover spectate args.

**ASA-SERVER** is for developing and proving the spectator, CLI, and services. The phases are in `AGENTS.md` (unit, then build, then one replay, then 1–5 full games only when the loop itself changed). Stop with `heroesreplay services stop`, which also closes Heroes of the Storm. If you kill `heroesreplay` yourself, close the game too (`CloseMainWindow`, then `Kill` if it does not exit). An open client with no spectator is a stuck replay. Start Twitch ingest only to prove the stream path: ASA-SERVER's OBS streams to a developer Twitch account, not `saltysadism` (`AGENTS.md`, Environments). **DESKTOP-8SJEK72** is the production spectate and live stream. Do not kill or rebuild it.

## Commands

| Command | Behavior |
| --- | --- |
| `spectate file [--file path] [--player Name#1234]` | Play one `.StormReplay` or each file in a directory, then exit. `--file` defaults to `Location:ReplaySource`. `--player` follows the player with that BattleTag while their hero is alive (the normal camera when that BattleTag did not play). A `--player` that is not a BattleTag, or a `--file` path that does not exist, is a parse error (exit 1). Exits 1 when the engine stops on an unexpected error. Starts the Aspire dashboard when OTLP :4317 is down; dashboard failure does not fail the replay. With clips on (`OBS:RecordingEnabled`), logs one error at start when ffmpeg or ffprobe cannot be found (`check ffmpeg`, `deps install`); the replay still plays. |
| `spectate heroesprofile` | Play `.StormReplay` files already in `Data\Standard` and `Data\Requests`. Does not call Heroes Profile. Same dashboard startup and clip-tool error as `spectate file`. |
| `heroesprofile download` | List and download Storm League replays into `Data\Standard`, and requested replays into `Data\Requests`. A Standard replay on the newest installed client (the current patch) comes first, even past a lower id on an older build, because upload order does not follow the client build. With none listed up to the newest id, it takes the first replay on an older build: installed, or on the supported patch line (`Spectate:MinimumGameVersion` and newer) and not installed, because spectate opens that replay through HeroesSwitcher and Blizzard downloads the client. It skips a build newer than the current patch and a build held in `Data\client-download-holds.json` after a failed download (`Spectate:BuildDownloadHold`, 4 h). It stops while `HeroesProfileApi:CachedReplayLimit` (5) Standard replays inside their media window wait (`ReplayMedia` candidate max age from the game date, the rule behind `records False (expired)`). A waiting replay past its window stays on disk as filler and does not count, so an old backlog cannot stop fresh downloads (#280); spectate plays newest first. A listed replay already past its window is downloaded only while fewer than that limit wait in total. Does not launch the game. While `YouTube:Titles:StatHooks:Enabled` is on, it also keeps the hero statistics for YouTube title hooks current beside the download loop (see `heroesprofile hero-stats`). |
| `heroesprofile hero-stats` | Fetch the Heroes Profile hero statistics behind YouTube title hooks now (issue #272): `/patches` picks the newest major patch, then `/heroes`, one `/heroes/stats?group_by_map=true`, and one `/heroes/matchups` per hero for each `HeroesProfileApi:HeroStats:GameTypes` entry (Storm League), collecting each 202 from `/jobs/{id}` after its `Retry-After`. Writes `DataHeroesProfilehero-stats<patch>-<code>.json` (`2.57-sl.json`) and deletes files older than the newest two patches. Runs whatever the file age and whether or not `YouTube:Titles:StatHooks:Enabled` is on; the download role does the same every `RefreshInterval` (24 h) while it is on. About 92 calls (of the weekly allowances) and 15 to 20 minutes. Exit 1 on a 401 or 403 (key or plan), a 422, or when nothing was written. Spectate only reads the file. |
| `heroesprofile patch-index [--write]` | Find the first Heroes Profile replay id on the latest replay's patch line. `--write` stores it as `MinReplayId` in `appsettings.json`. |
| `heroesprofile sample --map <name> --output <dir> [--count 2] [--game-type StormLeague\|QuickMatch\|ARAM]` | Download the newest replays of one map into a folder of their own, named like the cache, for `calculators units` and `calculators report`. Refuses a spectate queue folder. With no match it lists the maps in the newest listing pages. Quick Match and ARAM also need `HeroesProfileApi:GameTypes` to include them (dev lists Storm League only), for example `HEROES_REPLAY_HeroesProfileApi__GameTypes__1="Quick Match"`. Maps out of the Storm League rotation (Hanamura, Blackheart's Bay, Warhead Junction) come from Quick Match. |
| `services start [--supervise] [--roles r1,r2]` | Start `spectate heroesprofile`, `twitch connect`, `heroesprofile download`, and `youtube uploader` as separate processes, each in its own console window. Pid files go under `%LOCALAPPDATA%\HeroesReplay\logs`, next to each role's rolling log file (`<role>-<yyyy-MM-dd>.log`, see below). Updates the OBS collection paths first when OBS is closed. Does not start Twitch ingest. Starts the Aspire dashboard first when OTLP :4317 is not listening; a dashboard failure does not fail the services. `--roles download,youtube` starts only those roles, in plan order (for proofs; an unknown name exits 1). `--supervise` keeps this console as the supervisor once every role is ready (same as `services supervise`). Refuses (exit 1) while a supervisor is running in this session or another, checked before anything starts, the same way as `services supervise`. |
| `services supervise` | Supervise the roles in `services.json`, in the foreground, until `services stop` or Ctrl+C (Ctrl+C leaves the roles running unsupervised). One supervisor across logon sessions. The named mutex `Local\HeroesReplay.ServiceSupervisor` exists per session, and another logon session (SSH, `stream-pc-claude`) cannot see the desktop's, so there `supervisor.json` decides (see `services status`). This command and `services start [--supervise]` check both before they take the mutex. While a supervisor runs, they exit 1 with `supervisor already running: pid N, seen via supervisor.json` (`seen via its mutex` in the same session) and leave `supervisor.json` untouched (#293). Uses the `services status` classification each `ServiceRestart:PollInterval` (1s). A `failed` role restarts through the same launch as `services start` (arguments, new nonce, ready handshake) after `ServiceRestart:Backoff` (10s, 30s, 2m, 5m; the last repeats; the step is the restarts already in the window). A role whose heartbeat is `StaleRestartAfter` (2m) old is killed, then restarts the same way. Every attempt counts against `Budget` (5) per `BudgetWindow` (30m); a role that fails with the budget used stays down, logs one error, and reports `service.restart_budget_exhausted`. Degraded and stopped roles are left alone, except spectate degraded with `spectate.launch_stalled`, which is killed with a WRN and restarts like a failed role while the budget has room. Before spectate restarts, a game the dead spectator left open is closed; the supervisor never opens OBS or the game itself. It writes `supervisor.json` and its own `supervisor-<date>.log`. |
| `services install-task [--environment env] [--roles r1,r2] [--name n] [--remove]` | Register the Windows scheduled task `HeroesReplay-live`: `services start --supervise` from this install 30 s after you log on, interactive and not elevated (no administrator rights). `--environment` sets `HEROES_REPLAY_ENV` for it (default: this shell's). `apply-release.ps1` restarts the stack through it, so an update leaves the stack supervised. `--remove` deletes it. Run it once from the release install on the stream PC: `heroesreplay services install-task --environment prod`. |
| `services stop` | Write `services.stop`, wait for a running supervisor to exit (30s, then kill it), wait up to 20s for the roles, kill any `heroesreplay` pid still recorded, and close Heroes of the Storm. A role the supervisor was restarting when the stop arrived is in `services.json` and is stopped too. Prints each role (and the supervisor) as `graceful`, `killed`, `already exited`, or `still running`. After every role has exited it reads OBS `GetStreamStatus` once; it never stops the stream. Exits 1 when a role or the supervisor is still running (the stop file then stays down, so nothing restarts), the game is still open, or OBS is still streaming or did not report its stream state. A closed OBS counts as not streaming. A running OBS whose websocket does not answer fails the stop when this install streams (`OBS:StreamingEnabled`), because the stream may still be live; otherwise it is not checked. Do not leave the game client open after this. |
| `services status [--output text\|json]` | Classify each role from its heartbeat as `ready`, `degraded`, `stale`, `stopped`, or `failed`, with the cause and the fix, plus `status.json`. Each role rewrites its ready file every `ServiceHealth:HeartbeatInterval` (15s) with pid, path, version, readiness, `lastSuccessfulWorkAt`, and `lastError`. Stale is a live pid whose heartbeat is older than 3 intervals. Degraded is a fresh heartbeat whose last successful work is older than the role's `ServiceHealth:<Role>WorkThreshold`, or whose last error is newer than it. Spectate work is match progress only (the match clock advanced, or a session reached the clock or the award screen); after `ServiceHealth:SpectateNoProgressSessions` (3) sessions in a row without it, spectate is degraded with `causeCode` `spectate.no_match_progress`, `sessionsWithoutProgress`, and `lastOutcome`. When one replay's launch and loading phase (`launchingSince`) passes `ServiceHealth:SpectateLaunchStallThreshold` (20 min) without match progress, spectate is degraded with `causeCode` `spectate.launch_stalled`, which a supervisor kills and restarts within its budget. Each role also probes its live dependency before ready and every `ServiceHealth:DependencyProbeInterval` (10 min; 2 min while failing; bounded by `DependencyProbeTimeout` 10s) and writes it as `dependency` (`name`, `state` ok/rejected/unreachable/skipped/unused, `code`, `cause`, `remediation`, `checkedAt`, `since`): download one Heroes Profile replay-list call, youtube a token refresh at Google (no YouTube quota), twitch the token validator, spectate a read-only OBS identify (off until its live proof, `SpectateObsProbe`). A rejected or unreachable probe makes the role degraded with `causeCode` `download.heroesprofile_rejected`/`_unreachable`, `youtube.oauth_invalid`/`oauth_missing`/`oauth_unreachable`, `twitch.token_invalid`/`twitch.unreachable`, or `spectate.obs_rejected`/`obs_unreachable`, and the fix in `remediation`; the supervisor never restarts it, and a passing probe clears it (#305). The text shows `Probe: <name> <state>, checked Ns ago.` `sessionOutcomes` counts how each of the process's sessions ended. Failed is a recorded role that exited without a stop request. Each role shows its log file (`logPath`: the newest `<role>-*.log`, or today's when there is none). With a supervisor, each role shows `restarts` (`count`, `lastRestartAt`, `lastReason` failed/stale/launch_stalled, `lastFailure`, `nextRestartAt`, `budgetUsed`, `budgetLimit`, `budgetWindowSeconds`, `budgetExhausted`) and the envelope has `supervisor` (`running`, `seenVia`, `detail`, `pid`, `supervised`, `backoffSeconds`, `budget`, `budgetWindowSeconds`, `staleRestartAfterSeconds`, `logPath`). The supervisor's mutex decides `running` when this session can see it (`seenVia` `mutex`). Over SSH it cannot, so `supervisor.json` decides (`seenVia` `supervisor.json`): running only when its pid is alive, that process's start time matches `processStartedAt` (a reused pid does not count), and `updatedAt` is under 4 heartbeat intervals (60s) old. The text says how it decided, e.g. `Supervisor: running (pid 14420, seen via supervisor.json; mutex not visible from this session)`, or `not running (pid 14420 left supervisor.json; no process has pid 14420)`. `--output json` prints `{schemaVersion, ok, code, message, environment, checkedAt, stopRequested, roles[], spectator, supervisor}` with codes `service.ready`, `service.degraded`, `service.stale`, `service.stopped`, `service.failed`, and `service.restart_budget_exhausted` (a failed role the supervisor gave up on; it wins the envelope code). Exits 1 when a role is failed, stale, or degraded. |

| `youtube uploader` | Watch `Data\Contexts` for `.mp4` + `youtube-entry.json`. `YouTube:DryRun` true (dev and base) writes `youtube-dry-run.json` with the planned `PublishAtUtc` and insert settings, plans in `Data\publication-reservations-dry-run.txt`, and does not call YouTube. Production (`HEROES_REPLAY_ENV=prod`) sets `DryRun` false, `YouTube:Enabled` true, and `OBS:RecordingEnabled` true, so every spectated replay is recorded from the loading screen until the MVP screen and this process uploads it. A recording is uploaded as soon as its upload bucket allows: `videos.insert` calls today in `Data\youtube-quota-units.json` stay under `YouTube:DailyUploadCalls` (100) less `YouTube:UploadCallReserve` (5), and under `MaxInsertsPerQuotaDay`. Uploads no longer spend the 10,000-unit pool (`DailyQuotaUnits`), which is left to the library pass (#250). Production publishes up to 12 a day (`MaxPublicPerDay`, 2 of them reserved for requests). Every insert is private, not made for kids, and not age-restricted. A public listing gets `publishAt` at the earliest time the `ReplayMedia` limits allow (`MaxPublicPerDay`, `MaxPublicPerWeek`, `MinimumPublicInterval`, reserved request room, map, rank, and hero cooldowns), up to `MaxPublishAhead` (3 days in production) ahead; a request is sent first and is not paced: it publishes as soon as it is uploaded. Only the quota, the media rules, or no time inside `MaxPublishAhead` leave a recording on disk. The mp4 is deleted on the sweep after the insert. A scheduled upload keeps `VideoId` and `PublishAtUtc` on `youtube-entry.json`; an insert that YouTube already reports public saves them on `youtube-entry-uploaded.json`. Real uploads need `Data\client_secrets.json`. `services start` launches this process. Each successful insert appends a line to `Data\youtube-library.jsonl`, which retention never deletes. It also runs the `youtube library` pass in its own loop, 2 minutes after start (`YouTube:LibraryStartupDelay`) and then every `YouTube:LibraryInterval` (1 hour), whatever the upload backlog; that background pass never asks for consent and is skipped, with a warning, until `youtube library --once` has granted the `{ChannelId}-library` consent at the machine. An upload cut off mid-send (a release restart, `services stop`, a network failure) is retried automatically up to `YouTube:InterruptedUploadRetries` (5) times: the saved upload session is checked first, so a send that had finished is recorded and never inserted twice, and a publish time that passed is rescheduled. It is the only process that calls YouTube; the spectator's duplicate check reads `Data\youtube-replay-ids.txt` and the receipts only. |
| `youtube library [--once]` | Run the uploader's library pass now. Lists the channel's uploads with the `{ChannelId}-library` consent (full `https://www.googleapis.com/auth/youtube` scope), adds every replay id to `Data\youtube-replay-ids.txt`, records videos missing from `Data\youtube-library.jsonl` (Heroes Profile fills a missing map, mode, rank, or build; unresolved videos retry with backoff), and files each public video, newest first, into the groups `YouTube:Playlists` turns on: `Map` (`Alterac Pass`, every mode), `Mode` (`Storm League`, `Quick Match`, `ARAM`), `Rank` (`Storm League - Diamond`, division dropped), `Draft` (`Unusual drafts - Double healer`, one per `Draft:` note), `ViewerReview` (`Viewer requested reviews`, a request that named a player, i.e. a `Featured:` line), and `Patch` (`Patch {line}`, or the season name, for the current line; `Patch {line} archive` for older lines). All six are on by default; `MapMode` (the earlier `{Map} - Storm League - {League}` playlists) is off. Clips go into the patch playlist only; old-template videos have no draft note or request, so they get map, mode, rank, and patch. Each insert is 50 units: 4 (200 units) for a ranked Storm League video with the defaults, +1 per draft note, +1 for a review. Prints the planned inserts. `--once` runs one pass and exits; without it the pass repeats each `YouTube:LibraryInterval` until stopped. Shares the uploader's daily units in `Data\youtube-quota-units.json` (`LibraryUnitsPerDay` 3000, `DailyQuotaUnits` 10000 minus `QuotaReserveUnits` 500; uploads have their own bucket) and its lock, so the two cannot double-spend. A quota response pauses the pass until the next Pacific day. Not started by `services start`; `youtube uploader` runs the same pass there. Run it once at a machine to grant the library consent: the uploader's background pass never opens a browser. Dry-run writes `Data\youtube-library-dry-run.json` (the planned inserts, videos per playlist, and `InsertUnits`) and calls neither YouTube nor Heroes Profile. Playlist ids are cached in `Data\youtube-playlists.json`. Existing playlists are filed first; then at most `YouTube:LibraryMaxNewPlaylistsPerPass` (3) new playlists are created, the one the most items wait for first, after one `playlists.list` lookup so a playlist already on the channel is never created twice. A throttled `playlists.insert` (429) only ends the creates for that pass; its items stay planned. |

| `update preserve-min-replay-id` / `update release-health --since <utc> [--install dir] [--environment env] [--window hh:mm:ss] [--wait]` | Called by `apply-release.ps1`. The first keeps the higher `MinReplayId` when a release replaces `appsettings.json`. The second is the post-install health gate: exit 0 once every role in `services.json` runs with a fresh `ready/<nonce>.json` heartbeat from a process started after `--since` and spectate shows match progress after it (`lastSuccessfulWorkAt`: the match clock or the award screen); 1 while `Release:HealthWindow` (20 min) is open (without `--wait`); when it closes, 2 if a role is down or stale or spectate tried replays and none reached a clock (roll back), 4 if spectate had nothing it could play (empty queue, outage, only `BuildNotInstalled`/`VersionMismatch`/`RegionUnavailable`: inconclusive, keep the install); 3 when `services.stop` is down (no verdict). `--wait` checks every 15 s until a verdict. |
| `update migrate-stream-arm --previous <dir> [--environment env]` / `update install-obs --install <dir> [--environment env]` | Called by `apply-release.ps1`. The first arms the machine once when the replaced install's effective `OBS:StreamingEnabled` is true (never when false, never twice). The second first checks the install's `obs` folder against `obs\bundle.manifest` and refuses a mismatch (`obs.bundle_invalid`, exit 1, nothing written; no manifest installs with a warning), then copies the scene collection while OBS is closed and installs the profile template only when the machine has no profile. Do not run them by hand on a dev box: they write `%LOCALAPPDATA%\HeroesReplay` and `%APPDATA%\obs-studio`. |
| `update launcher --install <dir> [--environment env] [--state-dir dir]` / `update launcher --restore` | Called by `apply-release.ps1`. When `%LOCALAPPDATA%\HeroesReplay\start-live.cmd` exists, the new build rewrites it to `services start --supervise` with every role (keeping its `set HEROES_REPLAY_…` lines) and keeps the replaced one as `start-live.cmd.previous`. A hand-made launcher that started roles in `cmd /k` windows, or only some roles, hid the stack from the health gate. `--restore` puts `start-live.cmd.previous` back on a rollback. |
| `mcp` | Stdio MCP server. Logs on stderr. Snapshot: `%LOCALAPPDATA%/HeroesReplay/status.json`. Read-only OBS tools: `obs_inspect`, `obs_validate`, `obs_screenshot` |

New commands go on `HeroesReplayCommand` and need a **Smoke** test in `src/HeroesReplay.Tests/Smoke`.

## Role logs and supervision

Every role `services start` (or the supervisor) launches writes `%LOCALAPPDATA%\HeroesReplay\logs\<role>-<yyyy-MM-dd>.log` itself, whether or not Aspire is up; the supervisor writes `supervisor-<date>.log`. One line per entry: local time with offset, `INF`/`WRN`/`ERR`, category, message; exception lines are indented. A restart appends under a `--- <role> pid <n> version <v> ---` header. Tokens are redacted with the heartbeat `lastError` rules (`token=`, `api_key=`, `password=`, `Bearer`, `oauth:`). `ServiceLogs`: `Directory` (empty = that folder), `MaxFileSizeMegabytes` 20 (then `<role>-<date>.1.log`, `.2.log`), `RetainedDays` 14, `MaxFilesPerRole` 50. The level is `Logging:RoleFile` (Information; `System`/`Microsoft` Warning). A role run by hand, without `services start`, does not write the file. Read a live file with `Get-Content -Tail 50 -Wait`; `services status` names each role's file.

Production (`DESKTOP-8SJEK72`, in scheduled downtime for the first switch): run `heroesreplay services install-task --environment prod` once from `C:heroesreplaypp`, then `schtasks /Run /TN HeroesReplay-live` (or log on again). The task starts `services start --supervise` in its own console; leave it open. When spectate uses its restart budget and stays down, the supervisor makes a live stream safe: `ServiceRestart:SpectateDownObs` `WaitingScene` (default) shows `OBS:WaitingSceneName`, `StopStream` stops it, `None` leaves it. `heroesreplay services stop` stops the roles and the supervisor. If the supervisor console was closed, `heroesreplay services supervise` attaches to the running roles. Restart rules are `ServiceRestart` (`Backoff`, `Budget`, `BudgetWindow`, `StaleRestartAfter`, `PollInterval`). On ASA-SERVER prove with `HEROES_REPLAY_ENV=dev` and `--roles download,youtube` only.

## MCP (agent monitor)

Discovery: `.mcp.json` at the repo root (`dotnet run … -- mcp`) and `.grok/config.toml` register `heroesreplay` for the source tree; the release zip ships `.mcp.json` that starts `${HEROESREPLAY_APP:-C:\heroesreplay\app}\heroesreplay.exe mcp` with `HEROES_REPLAY_ENV` defaulting to `prod`. Every tool is annotated read-only and returns a typed object as MCP structured content with an output schema (`McpToolContractTests`), except `obs_screenshot`, which returns an image. Tools:

- `get_spectator_status` — `status` (phase, timer, replay, focus, OBS session, stale flag), `statusFile`, `gameProcess` (`processName`, `count`, `ids`, `error`)
- `check_battlenet` — Play or Update on the Battle.net window
- `get_current_focus` — `spectatorRunning`, `snapshotStale`, `phase`, `timer`, `focus`
- `check_config` / `check_heroesprofile` / `check_obs` / `check_twitch` — the CLI check result: `name`, `ok`, `detail`
- `obs_inspect` — live OBS, read-only (structured content, `schemaVersion` 1): versions and `availableRequestCount`, active profile and collection against `OBS:ProfileName` / `OBS:SceneCollectionName`, video base/output size and FPS, `profile` (output mode, recording format, encoders, `streamBitrateKbps`, `streamRateControl`, `recordingQuality`, `recordingBitrateKbps`, `recordingRateControl`, `recordingSharesStreamEncoder`), `recordDirectory`, program scene, scenes with items (name, kind, enabled), inputs with kind, mute, and volume (`globalAudio` is `desktop1`, `mic1`, … for the global devices), stream and record status, `GetStats` (render and encoding lag), `streamService` (`type` and `keySet` only), and `streamArm` (`armed`, `streamingEnabled`, `mayStart`, `blockedBy`). A failed request is listed in `unread`
- `obs_validate` — the loaded collection against the packaged `obs/Default.json` contract (`ObsContract`: game, waiting, and report scenes, the info, tier, and rank sources in the game scene, each report browser source). `findings` have a `code`, `severity` (`error` fails `ok`, `warning` does not), `subject`, and `message`. Codes: `obs.profile_mismatch`, `obs.collection_mismatch`, `obs.selection_unreadable`, `obs.scene_missing`, `obs.source_missing`, `obs.source_kind_mismatch`, `obs.scene_item_missing`, `obs.file_missing`, `obs.url_invalid`, `obs.mic_enabled`, `obs.request_unavailable`, `obs.asset_missing`, `obs.bundle_missing`, `obs.bundle_invalid` (an install file whose size or SHA-256 differs from `obs/bundle.manifest`, or a contract name `Default.json` lacks; one per file), `obs.canvas_mismatch` (base resolution not 1920x1080), `obs.stream_key_missing` (only when `OBS:StreamingEnabled`), `obs.recording_format` (not an .mp4 format while `OBS:RecordingEnabled`) (errors); `obs.runtime_file_missing` (a file under `Location:DataDirectory` the spectator writes), `obs.path_stale` (exists, but this install's rewrite points elsewhere), `obs.mic_muted`, `obs.collection_custom`, `obs.bundle_unverified` (no `obs/bundle.manifest`, so the files were not checked), `obs.fps_low` (below 30), `obs.scene_item_misplaced` (a contract item or game capture more than 2 px or 0.01 scale from `obs/Default.json`, or anchored or bounded differently), `obs.bitrate_low` (stream or recording video bitrate below the floor for the output size and FPS: 4500 kbps at 1080p60, 3000 at 1080p30 or 720p60, 2000 below), `obs.profile_unreadable`, `obs.recording_format` (when this install does not record), `obs.stream_service_unexpected` (not the named Twitch service), `obs.filter_missing` (a filter `obs/Default.json` gives a source), `obs.filter_stale` (an enabled Scroll filter `obs/Default.json` does not give a browser source) (warnings). Web URLs are checked for form only and never echoed
- `obs_screenshot` — `source` (default: program scene) and `width` (default 960, capped at 1920); returns a real MCP `image/png` block plus one text line

The OBS tools send only the Get requests in `ObsReadOnly` and resolve only `OBS:WebSocketPassword`. Each call opens its own short session (3 s identify timeout), reads, and disconnects; the spectator's one session per replay is not touched. When OBS is closed they return `ok: false` with `code: obs.unreachable`; other tool-level codes are `obs.auth_failed`, `obs.password_unresolved`, `obs.settings_unreadable`, `obs.request_failed`, and `obs.source_not_found` (screenshot of an unknown source). `obs_screenshot` returns `isError` with `code: message`. No MCP tool changes OBS: fixes go through guarded CLI commands (`obs arm` / `obs disarm`, later `obs plan` / `apply`). The stream key never leaves `ObsStreamService.Summarize`.

The MCP process is **not** the spectator. Run `spectate file` (or heroesprofile) separately; it writes the status file every second. If `updatedAt` is older than 15s, `snapshotStale` is true and `spectatorRunning` is false.

A local end-to-end run is not done until both patch launches have reached the match clock. The newest installed `Versions\Base*` exe signs in through Battle.net before the replay file is opened. An older installed exe is started by HeroesSwitcher with the replay file, not by Battle.net Play. A `Base*` folder with no executable is missing and must not launch the current client: a retained copy in `Data\Clients` is restored first, otherwise an older missing build opens through HeroesSwitcher and Blizzard downloads it (up to `Spectate:BuildDownloadLimit`, 10 min, for the exe to appear; a build that never arrives is held for `Spectate:BuildDownloadHold`, 4 h). See `AGENTS.md` "Current patch and previous patch".

Do not write to stdout from MCP tools (stdio is JSON-RPC).
