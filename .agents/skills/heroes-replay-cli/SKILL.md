# heroesreplay CLI

Entry: `src/HeroesReplay.CLI`. Assembly name `heroesreplay`. System.CommandLine 2 (`Subcommands`, `SetAction`). No command needs administrator rights except `client firewall`. `spectate` runs unelevated (issue #133): launching Battle.net and HeroesSwitcher, PrintWindow capture, the client memory reads (clock, screens, dialogs), and hotkeys all work at normal integrity. Spectate uses no OCR (#292); only `check battlenet` OCRs, and only the Battle.net launcher window. Only adding Windows Firewall rules needs an elevated shell. Invalid input is a parse error and exits 1 before anything runs.

```powershell
dotnet run --project src/HeroesReplay.CLI --no-launch-profile -- <command>
```

`--no-launch-profile` is required; launchSettings would otherwise inject leftover spectate args.

**ASA-SERVER** is for developing and proving the spectator, CLI, and services. The phases are in `AGENTS.md` (unit, then build, then one replay, then 1–5 full games only when the loop itself changed). Stop with `heroesreplay services stop`, which also closes Heroes of the Storm. If you kill `heroesreplay` yourself, close the game too (`CloseMainWindow`, then `Kill` if it does not exit). An open client with no spectator is a stuck replay. Start Twitch ingest only to prove the stream path: ASA-SERVER's OBS streams to a developer Twitch account, not `saltysadism` (`AGENTS.md`, Environments). **DESKTOP-8SJEK72** is the production spectate and live stream. Do not kill or rebuild it.

## Commands

Per command, what must be true first, what it changes, what each exit code means, and the stable codes it prints: [`commands.md`](commands.md) in this folder. It is generated from the command tree and `CommandReference.Facts` (`src/HeroesReplay.CLI/Commands/CommandReference.cs`), and `AgentDocsTests` fails when a command or code has no entry or the file is stale. The table below is the long description.

| Command | Behavior |
| --- | --- |
| `spectate file [--file path] [--player Name#1234]` | Play one `.StormReplay` or each file in a directory, then exit. `--file` defaults to `Location:ReplaySource`. `--player` follows the player with that BattleTag while their hero is alive (the normal camera when that BattleTag did not play). A `--player` that is not a BattleTag, or a `--file` path that does not exist, is a parse error (exit 1). Exits 1 when the engine stops on an unexpected error. Starts the Aspire dashboard when OTLP :4317 is down; dashboard failure does not fail the replay. With clips on (`OBS:RecordingEnabled`), logs one error at start when ffmpeg or ffprobe cannot be found (`check ffmpeg`, `deps install`); the replay still plays. |
| `spectate heroesprofile` | Play `.StormReplay` files already in `Data\Standard` and `Data\Requests`. Does not call Heroes Profile. Same dashboard startup and clip-tool error as `spectate file`. |
| `heroesprofile download` | List and download Storm League replays into `Data\Standard`, and requested replays into `Data\Requests`. A Standard replay on the newest installed client (the current patch) comes first, even past a lower id on an older build, because upload order does not follow the client build. With none listed up to the newest id, it takes the first replay on an older build: installed, or on the supported patch line (`Spectate:MinimumGameVersion` and newer) and not installed, because spectate opens that replay through HeroesSwitcher and Blizzard downloads the client. It skips a build newer than the current patch and a build held in `Data\client-download-holds.json` after a failed download (`Spectate:BuildDownloadHold`, 4 h). It stops while `HeroesProfileApi:CachedReplayLimit` (5) Standard replays inside their media window wait (`ReplayMedia` candidate max age from the game date, the rule behind `records False (expired)`). A waiting replay past its window stays on disk as filler and does not count, so an old backlog cannot stop fresh downloads (#280); spectate plays newest first. A listed replay already past its window is downloaded only while fewer than that limit wait in total. A Standard replay whose download Heroes Profile refuses with an HTTP status (after the retries; a 429 waits for `Retry-After`) is skipped with its replay id and status logged, and is not counted as an outage (#346). Does not launch the game. While `YouTube:Titles:StatHooks:Enabled` is on, it also keeps the hero statistics for YouTube title hooks current beside the download loop (see `heroesprofile hero-stats`). |
| `heroesprofile hero-stats` | Fetch the Heroes Profile hero statistics behind YouTube title hooks now (issue #272): `/patches` picks the newest major patch, then `/heroes`, one `/heroes/stats?group_by_map=true`, and one `/heroes/matchups` per hero for each `HeroesProfileApi:HeroStats:GameTypes` entry (Storm League), collecting each 202 from `/jobs/{id}` after its `Retry-After`. Writes `DataHeroesProfilehero-stats<patch>-<code>.json` (`2.57-sl.json`) and deletes files older than the newest two patches. Runs whatever the file age and whether or not `YouTube:Titles:StatHooks:Enabled` is on; the download role does the same every `RefreshInterval` (24 h) while it is on. About 92 calls (of the weekly allowances) and 15 to 20 minutes. Exit 1 on a 401 or 403 (key or plan), a 422, or when nothing was written. Spectate only reads the file. |
| `heroesprofile patch-index [--write]` | Find the first Heroes Profile replay id on the latest replay's patch line. `--write` stores it as `MinReplayId` in `appsettings.json`. |
| `heroesprofile sample --map <name> --output <dir> [--count 2] [--game-type StormLeague\|QuickMatch\|ARAM]` | Download the newest replays of one map into a folder of their own, named like the cache, for `calculators units` and `calculators report`. Refuses a spectate queue folder. A download that still fails after the Heroes Profile retries (a 429 waits for `Retry-After`) is skipped (replay id and HTTP status logged, partial file deleted) and the next listed replay is tried, until `--count` are in the folder or the listing runs out; the summary lists each skip and its reason. Exit 1 only when none of the listed replays landed (#346). With no match it lists the maps in the newest listing pages. Quick Match and ARAM also need `HeroesProfileApi:GameTypes` to include them (dev lists Storm League only), for example `HEROES_REPLAY_HeroesProfileApi__GameTypes__1="Quick Match"`. Maps out of the Storm League rotation (Hanamura, Blackheart's Bay, Warhead Junction) come from Quick Match. |
| `services start [--supervise] [--roles r1,r2]` | Start `spectate heroesprofile`, `twitch connect`, `heroesprofile download`, and `youtube uploader` as separate processes, each in its own console window. Pid files go under `%LOCALAPPDATA%\HeroesReplay\logs`, next to each role's rolling log file (`<role>-<yyyy-MM-dd>.log`, see below). Updates the OBS collection paths first when OBS is closed. Does not start Twitch ingest. Starts the Aspire dashboard first when OTLP :4317 is not listening; a dashboard failure does not fail the services. `--roles download,youtube` starts only those roles, in plan order (for proofs; an unknown name exits 1). `--supervise` keeps this console as the supervisor once every role is ready (same as `services supervise`). Refuses (exit 1) while a supervisor is running in this session or another, checked before anything starts, the same way as `services supervise`. |
| `services ensure [--roles r1,r2] [--supervise] [--output text\|json]` | Idempotent `services start` for agents and scripts (#306): make sure the requested roles (default all four) run from this install. Starts only the ones that are down (failed, exited, or not in `services.json`), in plan order, through the same launch and startup checks as `services start`, and replaces only their records in `services.json`. Never stops or kills a role that was running; a ready or degraded role is left alone. Exit 0: `service.ensure_noop` (nothing to do; with `--supervise` a supervisor already runs) or `service.ensure_started` (started the missing roles and/or, with `--supervise` and no supervisor in any session, claimed the supervisor mutex before starting and stays in the foreground as the supervisor after the report). Exit 1, starting nothing, in this order: `service.ensure_stop_pending` (`services.stop` is down), `service.ensure_mismatch` (a live role runs from another install path or version; builds are not mixed), `service.ensure_budget_exhausted` (a requested role used its restart budget), `service.ensure_stale` (a requested role is alive but stale), `service.ensure_supervisor_running` (a requested role is down while a supervisor runs in any session; the report says whether and when the supervisor restarts it), `service.ensure_busy` (another ensure holds `services.ensure.lock`). `service.ensure_start_failed` (exit 1) kills what this ensure started and puts `services.json` back, so a failed ensure leaves the stack as it was. `--output json` is the `services status` envelope (`schemaVersion`, `ok`, `code`, `message`, `remediation`, `supervisorRunning`, `supervisorAttached`, `requested`, `started`, `roles[]` with `state`, `action` running/start/started/start_failed/blocked, `pid`, `detail`); launch lines go to stderr. On ASA-SERVER prove with `HEROES_REPLAY_ENV=dev` and `--roles download,youtube` only. |
| `services supervise` | Supervise the roles in `services.json`, in the foreground, until `services stop` or Ctrl+C (Ctrl+C leaves the roles running unsupervised). One supervisor across logon sessions. The named mutex `Local\HeroesReplay.ServiceSupervisor` exists per session, and another logon session (SSH, `stream-pc-claude`) cannot see the desktop's, so there `supervisor.json` decides (see `services status`). This command and `services start [--supervise]` check both before they take the mutex. While a supervisor runs, they exit 1 with `supervisor already running: pid N, seen via supervisor.json` (`seen via its mutex` in the same session) and leave `supervisor.json` untouched (#293). Uses the `services status` classification each `ServiceRestart:PollInterval` (1s). A `failed` role restarts through the same launch as `services start` (arguments, new nonce, ready handshake) after `ServiceRestart:Backoff` (10s, 30s, 2m, 5m; the last repeats; the step is the restarts already in the window). A role whose heartbeat is `StaleRestartAfter` (2m) old is killed, then restarts the same way. Every attempt counts against `Budget` (5) per `BudgetWindow` (30m); a role that fails with the budget used stays down, logs one error, and reports `service.restart_budget_exhausted`. Degraded and stopped roles are left alone, except spectate degraded with `spectate.launch_stalled`, which is killed with a WRN and restarts like a failed role while the budget has room. Before spectate restarts, a game the dead spectator left open is closed; the supervisor never opens OBS or the game itself. A restart owns what it starts (#397): a child whose launcher lost its pid is found by its nonce or command line, one not ready within `ServiceRestart:ReadyTimeout` (45s; `SlowReadyTimeout` 3m while commit is above `SlowReadyCommitPercent` 90%) is killed, and one that will not die stays in `services.json`. Before starting a role it takes over a live, heartbeating process of that role from this install that `services.json` does not track (`service.role_adopted`, no budget used) and kills one it cannot watch (`service.untracked_role_killed`). A restart that leaves no process keeps the role in `services.json` with pid 0, never a dead pid. It writes `supervisor.json` and its own `supervisor-<date>.log`. |
| `services install-task [--environment env] [--roles r1,r2] [--name n] [--remove]` | Register the Windows scheduled task `HeroesReplay-live`: `services start --supervise` from this install 30 s after you log on, interactive and not elevated (no administrator rights). `--environment` sets `HEROES_REPLAY_ENV` for it (default: this shell's). `apply-release.ps1` restarts the stack through it, so an update leaves the stack supervised. `--remove` deletes it. Run it once from the release install on the stream PC: `heroesreplay services install-task --environment prod`. |
| `services stop` | Write `services.stop`, wait for a running supervisor to exit (30s, then kill it), wait up to 20s for the roles, kill any `heroesreplay` pid still recorded, and close Heroes of the Storm. Then each `HeroesSwitcher_x64` with no Heroes child gets `CloseMainWindow`, then a kill after 5s; one whose Heroes child still runs is left (a handoff, or a game that did not close). The `Heroes of the Storm:` line names each switcher (`HeroesSwitcher_x64 pid 40108: closed.`, `killed`, `still running`, or `left running, its Heroes pid N is still up`), #359. A role the supervisor was restarting when the stop arrived is in `services.json` and is stopped too. Prints each role (and the supervisor) as `graceful`, `killed`, `already exited`, or `still running`. After every role has exited it reads OBS `GetStreamStatus` once; it never stops the stream. Then it stops the OBS recording spectate claimed and left running (`OBS recording:` line, #318): spectate writes `%LOCALAPPDATA%\HeroesReplay\obs-recording.json` when it starts a recording and deletes it when OBS finalizes the file. With a claim, stop reads `GetRecordStatus` and sends `StopRecord` only when the active recording's duration matches the claim's start (within 2 minutes, or a tenth of its age); a younger recording is someone else's and keeps running. It never sends `StopStream`. Exits 1 when a role or the supervisor is still running (the stop file then stays down, so nothing restarts), the game or a switcher without one is still open, OBS is still streaming or did not report its stream state, or a recording spectate started may still be running (OBS refused the stop, or its websocket did not answer while a claim exists). A closed OBS counts as not streaming. A running OBS whose websocket does not answer fails the stop when this install streams (`OBS:StreamingEnabled`), because the stream may still be live; otherwise it is not checked. Do not leave the game client open after this. |
| `services status [--output text\|json]` | Classify each role from its heartbeat as `ready`, `degraded`, `stale`, `stopped`, or `failed`, with the cause and the fix, plus `status.json`. Each role rewrites its ready file every `ServiceHealth:HeartbeatInterval` (15s) with pid, path, version, readiness, `lastSuccessfulWorkAt`, and `lastError`. Stale is a live pid whose heartbeat is older than 3 intervals. Degraded is a fresh heartbeat whose last successful work is older than the role's `ServiceHealth:<Role>WorkThreshold`, or whose last error is newer than it. Spectate work is match progress only (the match clock advanced, or a session reached the clock or the award screen); after `ServiceHealth:SpectateNoProgressSessions` (3) sessions in a row without it, spectate is degraded with `causeCode` `spectate.no_match_progress`, `sessionsWithoutProgress`, and `lastOutcome`. When one replay's launch and loading phase (`launchingSince`) passes `ServiceHealth:SpectateLaunchStallThreshold` (20 min) without match progress, spectate is degraded with `causeCode` `spectate.launch_stalled`, which a supervisor kills and restarts within its budget. Each role also probes its live dependency before ready and every `ServiceHealth:DependencyProbeInterval` (10 min; 2 min while failing; bounded by `DependencyProbeTimeout` 10s) and writes it as `dependency` (`name`, `state` ok/rejected/unreachable/skipped/unused, `code`, `cause`, `remediation`, `checkedAt`, `since`): download one Heroes Profile replay-list call, youtube a token refresh at Google (no YouTube quota), twitch the token validator, spectate a read-only OBS identify (off until its live proof, `SpectateObsProbe`). A rejected or unreachable probe makes the role degraded with `causeCode` `download.heroesprofile_rejected`/`_unreachable`, `youtube.oauth_invalid`/`oauth_missing`/`oauth_unreachable`, `twitch.token_invalid`/`twitch.unreachable`, or `spectate.obs_rejected`/`obs_unreachable`, and the fix in `remediation`; the supervisor never restarts it, and a passing probe clears it (#305). The text shows `Probe: <name> <state>, checked Ns ago.` `sessionOutcomes` counts how each of the process's sessions ended. Failed is a recorded role that exited without a stop request. Each role shows its log file (`logPath`: the newest `<role>-*.log`, or today's when there is none). With a supervisor, each role shows `restarts` (`count`, `lastRestartAt`, `lastReason` failed/stale/launch_stalled, `lastFailure`, `nextRestartAt`, `budgetUsed`, `budgetLimit`, `budgetWindowSeconds`, `budgetExhausted`) and the envelope has `supervisor` (`running`, `seenVia`, `detail`, `pid`, `supervised`, `backoffSeconds`, `budget`, `budgetWindowSeconds`, `staleRestartAfterSeconds`, `logPath`). The supervisor's mutex decides `running` when this session can see it (`seenVia` `mutex`). Over SSH it cannot, so `supervisor.json` decides (`seenVia` `supervisor.json`): running only when its pid is alive, that process's start time matches `processStartedAt` (a reused pid does not count), and `updatedAt` is under 4 heartbeat intervals (60s) old. The text says how it decided, e.g. `Supervisor: running (pid 14420, seen via supervisor.json; mutex not visible from this session)`, or `not running (pid 14420 left supervisor.json; no process has pid 14420)`. The `Machine:` line (`machine`) is memory, commit charge, and the Agent.exe, conhost.exe, and Heroes counts, with a `WARN` per value above its `MachineHealth` limit; while memory or commit is above its limit it also lists the `MachineHealth:TopConsumerCount` (5) processes holding the most private bytes (commit), whoever owns them (`machine.topConsumers`: `name`, `pid`, `privateMegabytes`, `workingSetMegabytes`, `startedAt`). Report only: nothing is stopped (#399). A machine warning never changes `ok` or the exit code. `--output json` prints `{schemaVersion, ok, code, message, environment, checkedAt, stopRequested, roles[], spectator, supervisor, machine}` with codes `service.ready`, `service.degraded`, `service.stale`, `service.stopped`, `service.failed`, and `service.restart_budget_exhausted` (a failed role the supervisor gave up on; it wins the envelope code). Exits 1 when a role is failed, stale, or degraded. |

| `youtube uploader` | Watch `Data\Contexts` for `.mp4` + `youtube-entry.json`. `YouTube:DryRun` true (dev and base) writes `youtube-dry-run.json` with the planned `PublishAtUtc` and insert settings, plans in `Data\publication-reservations-dry-run.txt`, and does not call YouTube. A recording is uploaded as soon as its upload bucket allows: `videos.insert` calls today in `Data\youtube-quota-units.json` stay under `YouTube:DailyUploadCalls` (100) less `YouTube:UploadCallReserve` (5), and under `MaxInsertsPerQuotaDay`. Uploads no longer spend the 10,000-unit pool (`DailyQuotaUnits`), which is left to the library pass (#250). Production publishes up to 12 a day (`MaxPublicPerDay`, 2 of them reserved for requests). Every insert is private, not made for kids, and not age-restricted. A public listing gets `publishAt` at the earliest time the `ReplayMedia` limits allow (`MaxPublicPerDay`, `MaxPublicPerWeek`, `MinimumPublicInterval`, reserved request room, map, rank, and hero cooldowns), up to `MaxPublishAhead` (3 days in production) ahead; a request is sent first and is not paced: it publishes as soon as it is uploaded. ## JSON output contract (`--output text|json`)

`check` (every target), `obs status`, `obs inspect`, `obs validate`, `obs bundle`, `obs plan`, `obs backup`, `obs restore`, `config effective`, `client status`, `deps install`, `services status`, and `services ensure` take `--output text|json` (`-o`). Text is the default and is for people. Any other value, such as `yaml`, is a parse error: exit 1 before anything runs.

- **One document on stdout.** JSON mode prints exactly one JSON object. Logs, `check timer` samples, and `deps install` download progress go to stderr, so `heroesreplay check --output json | ConvertFrom-Json` works. The check services always log to stderr, which also keeps the MCP `check_*` tools off the JSON-RPC stream.
- **Envelope.** Every result starts with `schemaVersion` (1), `ok`, and a stable `code`, and the exit code is 0 exactly when `ok` is true. Exit codes are the same as in text mode. New commands use the shared `CliResult` envelope `{schemaVersion, ok, code, message, environment, details}`: `message` is one line for a person, `environment` is `HEROES_REPLAY_ENV` (null when unset), and `details` is the command's own payload. `services status`, `services ensure`, `obs inspect`, `obs validate`, `obs bundle`, `obs plan`, `obs backup`, `obs restore`, and `config effective` came first and keep their own fields after the first three (pinned by `CliResultTests`). `config effective` and `obs validate` have a null `code` when `ok`. Within schema version 1 a field may be added, never renamed or removed.
- **Codes.** A code is `<area>.<reason>` and is never reused for another reason. `check` codes are `check.<target>.<reason>`, with a hyphen in the target written as an underscore. Every target has `.ok` and `.error` (an unexpected exception, with the exception message as the detail).
- **Redaction.** No field carries a secret value. Secrets show as present or missing (`check config`). Every secret the command resolved (Heroes Profile key, Twitch token, refresh token, and client id, uploader key, OBS password, GitHub token, YouTube key) is replaced with `[redacted]` wherever it appears, in text and JSON alike, and then the role-log rules mask `token=`, `api_key=`, `key=`, `password=`, `Bearer <token>`, `oauth:<token>`, and any Google API key.

`check --output json`:

```json
{
  "schemaVersion": 1,
  "ok": false,
  "code": "check.obs.unreachable",
  "message": "1 of 8 check(s) failed: obs.",
  "environment": "dev",
  "details": {
    "checks": [
      { "name": "config", "ok": true, "status": "ok", "code": "check.config.ok", "detail": "..." },
      { "name": "obs", "ok": false, "status": "fail", "code": "check.obs.unreachable", "detail": "..." }
    ]
  }
}
```

`status` is `ok`, `warn` (passes; the detail has no `Warning:` prefix), or `fail`. The envelope `code` is the first failure's code, else the first warning's, else the only check's code, else `check.ok`.

## Role logs and supervision

Every role `services start` (or the supervisor) launches writes `%LOCALAPPDATA%\HeroesReplay\logs\<role>-<yyyy-MM-dd>.log` itself, whether or not Aspire is up; the supervisor writes `supervisor-<date>.log`. One line per entry: local time with offset, `INF`/`WRN`/`ERR`, category, message; exception lines are indented. A restart appends under a `--- <role> pid <n> version <v> ---` header. Tokens are redacted with the heartbeat `lastError` rules (`token=`, `api_key=`, `key=`, `password=`, `Bearer`, `oauth:`, a Google API key). `ServiceLogs`: `Directory` (empty = that folder), `MaxFileSizeMegabytes` 20 (then `<role>-<date>.1.log`, `.2.log`), `RetainedDays` 14, `MaxFilesPerRole` 50. The level is `Logging:RoleFile` (Information; `System`/`Microsoft` Warning). A role run by hand, without `services start`, does not write the file. Read a live file with `Get-Content -Tail 50 -Wait`; `services status` names each role's file.

Production (`DESKTOP-8SJEK72`, in scheduled downtime for the first switch): run `heroesreplay services install-task --environment prod` once from `C:\heroesreplay\app`, then `schtasks /Run /TN HeroesReplay-live` (or log on again). The task starts `services start --supervise` in its own console; leave it open. When spectate uses its restart budget and stays down, the supervisor makes a live stream safe: `ServiceRestart:SpectateDownObs` `WaitingScene` (default) shows `OBS:WaitingSceneName`, `StopStream` stops it, `None` leaves it. `heroesreplay services stop` stops the roles and the supervisor. If the supervisor console was closed, `heroesreplay services supervise` attaches to the running roles. Restart rules are `ServiceRestart` (`Backoff`, `Budget`, `BudgetWindow`, `StaleRestartAfter`, `PollInterval`). On ASA-SERVER prove with `HEROES_REPLAY_ENV=dev` and `--roles download,youtube` only.

- `obs_inspect` — live OBS, read-only (structured content, `schemaVersion` 1): versions and `availableRequestCount`, active profile and collection against `OBS:ProfileName` / `OBS:SceneCollectionName`, video base/output size and FPS, `profile` (output mode, recording format, encoders, `streamBitrateKbps`, `streamRateControl`, `recordingQuality`, `recordingBitrateKbps`, `recordingRateControl`, `recordingSharesStreamEncoder`), `recordDirectory`, program scene, scenes with items (name, kind, enabled), inputs with kind, mute, and volume (`globalAudio` is `desktop1`, `mic1`, … for the global devices), stream and record status, `GetStats` (render and encoding lag), `streamService` (`type` and `keySet` only), and `streamArm` (`armed`, `streamingEnabled`, `mayStart`, `blockedBy`). A failed request is listed in `unread`
- `obs_validate` — the loaded collection against the packaged `obs/Default.json` contract (`ObsContract`: game, waiting, and report scenes, the info, tier, and rank sources in the game scene, each report browser source). `findings` have a `code`, `severity` (`error` fails `ok`, `warning` does not), `subject`, and `message`. Codes: `obs.profile_mismatch`, `obs.collection_mismatch`, `obs.selection_unreadable`, `obs.scene_missing`, `obs.source_missing`, `obs.source_kind_mismatch`, `obs.scene_item_missing`, `obs.file_missing`, `obs.url_invalid`, `obs.mic_enabled` (a live microphone: a global Mic/Aux device or an audio input capture source; spectate mutes it with `OBS:MuteMicrophones`, so it never stops the stream, #314), `obs.request_unavailable`, `obs.asset_missing`, `obs.bundle_missing`, `obs.bundle_invalid` (an install file whose size or SHA-256 differs from `obs/bundle.manifest`, or a contract name `Default.json` lacks; one per file), `obs.canvas_mismatch` (base resolution not 1920x1080), `obs.stream_key_missing` (only when `OBS:StreamingEnabled`), `obs.recording_format` (not an .mp4 format while `OBS:RecordingEnabled`), `obs.recording_format_invalid` (`OBS:RecordingFormat` not `mp4`, `hybrid_mp4`, `fragmented_mp4`, or `mkv`) (errors); `obs.runtime_file_missing` (a file under `Location:DataDirectory` the spectator writes), `obs.file_unverifiable` (a path this session could not check: a junction or symbolic link on the way, such as `C:\heroesreplay` over SSH on the stream PC, that it can neither traverse nor read; a path whose junction it can read is checked at the junction's target instead), `obs.path_stale` (exists, but this install's rewrite points elsewhere), `obs.mic_muted`, `obs.collection_custom`, `obs.bundle_unverified` (no `obs/bundle.manifest`, so the files were not checked), `obs.fps_low` (below 30), `obs.scene_item_misplaced` (a contract item or game capture more than 2 px or 0.01 scale from `obs/Default.json`, or anchored or bounded differently), `obs.bitrate_low` (stream or recording video bitrate below the floor for the output size and FPS: 4500 kbps at 1080p60, 3000 at 1080p30 or 720p60, 2000 below), `obs.profile_unreadable`, `obs.recording_format` (when this install does not record), `obs.recording_not_crash_safe` (an .mp4 format other than `fragmented_mp4`, which a crash or power loss can lose; the spectator sets `OBS:RecordingFormat` before each recording, #310), `obs.stream_service_unexpected` (not the named Twitch service), `obs.filter_missing` (a filter `obs/Default.json` gives a source), `obs.filter_stale` (an enabled Scroll filter `obs/Default.json` does not give a browser source) (warnings). Web URLs are checked for form only and never echoed
- `obs_screenshot` — `source` (default: program scene) and `width` (default 960, capped at 1920); returns a real MCP `image/png` block plus one text line

The OBS tools send only the Get requests in `ObsReadOnly` and resolve only `OBS:WebSocketPassword`. Each call opens its own short session (3 s identify timeout), reads, and disconnects; the spectator's one session per replay is not touched. When OBS is closed they return `ok: false` with `code: obs.unreachable`; other tool-level codes are `obs.auth_failed`, `obs.password_unresolved`, `obs.settings_unreadable`, `obs.request_failed`, and `obs.source_not_found` (screenshot of an unknown source). `obs_screenshot` returns `isError` with `code: message`. No MCP tool changes OBS: fixes go through guarded CLI commands (`obs arm` / `obs disarm`; `obs plan` shows what an update would change and writes nothing; `obs backup` / `obs restore` keep and put back the collection while OBS is closed; `obs apply --backup` merges template changes into it while OBS is closed). The stream key never leaves `ObsStreamService.Summarize`.

The MCP process is **not** the spectator. Run `spectate file` (or heroesprofile) separately; it writes the status file every second. If `updatedAt` is older than 15s, `snapshotStale` is true and `spectatorRunning` is false.

A local end-to-end run is not done until both patch launches have reached the match clock. The newest installed `Versions\Base*` exe signs in through Battle.net before the replay file is opened. An older installed exe is started by HeroesSwitcher with the replay file, not by Battle.net Play. A `Base*` folder with no executable is missing and must not launch the current client: a retained copy in `Data\Clients` is restored first, otherwise an older missing build opens through HeroesSwitcher and Blizzard downloads it (up to `Spectate:BuildDownloadLimit`, 10 min, for the exe to appear; a build that never arrives is held for `Spectate:BuildDownloadHold`, 4 h). See `AGENTS.md` "Current patch and previous patch".

Do not write to stdout from MCP tools (stdio is JSON-RPC).
