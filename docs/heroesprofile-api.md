# Heroes Profile API

Canonical OpenAPI (do not vendor the 5MB file):

https://raw.githubusercontent.com/Heroes-Profile/heroesprofile/refs/heads/develop/public/spec/heroesprofile-v1.json

Base URL: `https://www.heroesprofile.com/api/external/v1/`  
Auth: `Authorization: Bearer <key>` (same key as the old `api_token`).

## Kiota client

`src/HeroesReplay.HeroesProfile.Client` is generated by Microsoft Kiota (`dotnet kiota`, local tool `microsoft.openapi.kiota` 1.29.0) plus `Microsoft.Kiota.Bundle` 1.22.2 (Abstractions ≥ 1.22.0 for GHSA-7j59-v9qr-6fq9). Hand-written factory/token types sit next to `Generated/`.

```powershell
dotnet tool restore
.\tools\generate-heroesprofile-client.ps1
```

Paths included: `/replays`, `/replays/**`, `/download/replay`, `/replay/{replayID}`. Do not csharpier `Generated/`. List and download always go through `HeroesProfileClient` with `Authorization: Bearer`.

Hand-written partials of `HeroesProfileClient` sit next to `Generated/` and use the same request adapter and key: `MmrTier.cs` (`/mmr/tier`) and `GlobalStats.cs` (`GetGlobalAsync`, `GetJobAsync`) for the global statistics. Those are not generated on purpose: an uncached global query answers 202 with a `job_id`, the result comes from `/jobs/{id}` in the shape of the original call (the spec has no model for it), and the spec leaves out fields we read (`win_rate`, `games_played`, `ban_rate`, `confidence_interval`). `GlobalStats.cs` returns the status, body, `Retry-After`, job id, and `error.code` without throwing, so the caller decides what a 202, 429, or error means. `ReplayDownload.cs` (`DownloadReplayAsync`) sends the generated `/download/replay` request but keeps an error answer's `error.code` (#361, below).

## Endpoints we use

| Call | Path |
| --- | --- |
| List / max id | `GET /replays?after={id}&game_type=Storm League` |
| Download | `GET /download/replay?replayID={id}` |
| One match | `GET /replays?after={id-1}` then pick `replayID` |
| Reward search (map and rank rewards) | `GET /replays?after={id}&game_type=…&game_map=…` (every match after `after`, oldest first, up to 1,000; there is no rank or MMR filter) |
| Rank badge, and a rank reward's candidates (#429) | `GET /replay/{replayID}` (average `player_mmr`), then `GET /mmr/tier?game_type=…&mmr=…`. Each game type has its own ladder: on 2026-10-13, 2,750 was Platinum 4 in `sl`, Diamond 4 in `qm` and Platinum 2 in `aram` |
| A listed candidate's score screen (interest pick, #510) | `GET /replay/{replayID}` (`players[]` per team, each with `team`, `hero.name` and `score`; `game_length` in seconds). The same cached answer serves the rank badge |
| Hero statistics: newest patch | `GET /patches` (newest `game_version` with `valid_globals`; `2.57.0.98348` is major `2.57`) |
| Hero statistics: ids | `GET /heroes` (`id`, `name`, `attribute_id`) |
| Hero statistics: every hero on every map | `GET /heroes/stats?timeframe_type=major&timeframe=2.57&game_type=sl&group_by_map=true` (one object per map, a `data` row per hero: `hero_id`, `wins`, `games_played`, `ban_rate`) |
| Hero statistics: one hero against and with each other | `GET /heroes/matchups?timeframe_type=major&timeframe=2.57&game_type=sl&hero=Valla` (`enemy[]` and `ally[]`, each with `hero.attribute_id`, `wins`, `games_played`) |
| A job's result | `GET /jobs/{id}` (202 still running, 200 the result) |
| Map list (Storm League pool check, #425) | `GET /maps` (`name`, `type`, `ranked_rotation`, `playable`) |
| A player's record on a hero (focus picks, #433) | `GET /players/heroes?battletag=Name%231234&region=2&game_type=sl&hero=Kael'thas` (an array with the hero's row: `wins`, `losses`, `games_played`, `kda`, `sl_mmr_data`, `sl_rank_tier`, `hero.attribute_id`) |
| Players who went private (#433) | `GET /players/privacy/changes?since=…&after_id=…&limit=1000` (`changes[]` with `battletag`, `region`, `state`; `next_since`, `next_after_id`, `has_more`) |

`region` is an integer (1 NA, 2 EU, 3 KR, 5 CN). List rows have `downloadable`. Skip when `downloadable` is false or `deleted` is non-zero.

Measured on 2026-10-13 (`x-hp-quota-limit`, rolling 7 days, and `x-ratelimit-limit` per minute): `/replays` allows 60,000 calls a week and 200 a minute, `/replay/{id}` 1,000,000 a week and 500 a minute, `/mmr/tier` 1,000,000 a week and 60 a minute, and `/maps` 1,000,000 a week. A rank reward stays within `/mmr/tier`'s minute with at most `HeroesProfileApi:RankLookupLimit` (40) lookups; a 429 waits for its `Retry-After` (1–3 s when measured). The `/replays` list is in replay-id order, which is upload order, not play order: old games are still being uploaded (replay 65960001 is a 2.55.5 game from July 2024), so a filter on `game_version` is what keeps a sample to the current patch.

`/maps` `ranked_rotation` is maintained by hand and lags. On 2026-10-13 it marked every standard map 1 except Blackheart's Bay, while Heroes Profile's own replays had no Storm League game on Hanamura Temple or Warhead Junction since 2.55.17.97605 (20 Jul 2026). `StormLeagueRotation` uses only its 0, and only when too few Storm League replays are cached to see the pool.

### Retries and rejected downloads

The replay calls above share one `HttpClient` (`heroes-profile`) with the `Microsoft.Extensions.Http.Resilience` pipeline in `HeroesProfileHttp`: a 2 min timeout per attempt and up to 10 retries. A network error, a timeout, or a 5xx is retried 1 s apart. A 429 waits for its `Retry-After` (1 s without one); a `Retry-After` longer than 1 minute is a quota, not the per-minute limit, so that 429 is not retried. When the last attempt still fails, Kiota throws `ApiException` with the HTTP status, and the caller skips that replay (#346): `heroesprofile sample` logs the replay id and status, deletes the partial file, tries the next listed replay, and prints a summary of what it downloaded and skipped; the download role logs the replay id and status and lists the replay after it, without counting the rejection as an outage.

A 401 or 403 on the replay list is a refused key, not a transient failure (#358): the same key gets the same answer until someone fixes it. The download role then pauses its listing (`ReplayListBackoff`): one list call every `ServiceHealth:DependencyRetryInterval` (2 min, the failing dependency probe's cadence), and none at all while its probe reports `download.heroesprofile_rejected`. A probe that passes, or a list Heroes Profile answers, resumes it at once. It logs one warning when the pause starts and one line when it ends, never one per call. A 429, a 5xx, a timeout, or no answer is unchanged: the pipeline above retries it, and the role lists again `HeroesProfileApi:APIRetryWaitTime` (1 s) later.

A Twitch reward request is different (#351): the viewer paid for that replay, so it is not skipped. It stays in `Data\requests.json` until its replay is renamed into `Data\Requests`, and leaves the queue in the same queue-locked step. A download Heroes Profile answers with 404 or 410, or with 403 and the body's `error.code` `replay_deleted` (Heroes Profile deleted the file: `{"error":{"code":"replay_deleted","message":"That replay is no longer stored.",...}}`, #361), or a replay whose client is now below `Spectate:MinimumGameVersion`, fails the request: it moves to `failed-requests.json` with its reason (`HTTP 403 replay_deleted`), the queue page lists it under "Could not play", and a `Cancel` line in `Data\redemption-dispositions.txt` has `twitch connect` cancel the redemption, which returns the points. Any other failure (a 429 or 5xx after the pipeline's retries, any other 403, which can be a key or plan problem, another status, a timeout, a network or disk error) keeps the request queued with its attempt count and retries it after 1, 2, 4, 8, 16, then every 30 minutes, without a refund; the requests behind it are not held back. A stop or a kill mid-download leaves the request as it was, and a kill after the replay landed leaves it queued with its replay on disk, so the next pass dequeues it without a second download.

The download is `HeroesProfileClient.DownloadReplayAsync`, a hand-written partial over the generated `/download/replay` request: the generated error mapping has no 403, so Kiota would drop that body. An error answer throws `HeroesProfileApiException` with the status and the body's `error.code`. It reads at most 16 KB of an error body and keeps only that code, and only when it is a short token (letters, digits, `_`, `-`, `.`), so no other body text reaches a log or `requests.json`.

### Interest pick (#510)

With `HeroesProfileApi:Interest:Enabled` (on in dev; off in base and prod until its numbers are reviewed), the download role does not simply take the lowest current-patch id. For one download it:

1. **Lists the candidates.** It keeps the page's first `Candidates` (20) current-patch replays that are still inside their media window.
2. **Reads each score screen.** It asks for each one's `/replay/{id}`, within `DetailTimeout` (20 s each). The answer is cached for 30 minutes, so the rank badge of the replay it takes needs no second call.
3. **Downloads the best.** `ReplayInterest` scores each candidate from facts on its score screen, and the highest score is downloaded. The listing cursor then moves past every candidate it scored.

What scores (the points only rank one page's candidates against each other):

| Signal | When it counts |
|---|---|
| Deathless carry | A player with 0 deaths and 8 or more kills |
| Kill leader | Another player with 10 or more kills and at most 1 death |
| Long takedown streak | 25 or more takedowns without dying |
| Time on fire | 300 s or more on fire |
| Team wipe | A takedown burst of 5. Every hero in that wipe gets `multikill` 5, so this is a team fight, not one hero's feat |
| Long game | 25 minutes or more |
| Short game | Under 13 minutes; this one takes points away |
| League | Diamond or higher, when the listing names a rank |

**Failures.** A candidate whose detail fails or times out is not scored. With none scored, the role takes the lowest id as before.

**Cost.** At about 30 downloads a day, 20 candidates each is about 600 `/replay/{id}` calls a day, roughly 0.4% of its weekly allowance. The list calls don't change.

**Tuning.** `heroesreplay calculators interest --directory <corpus> --recursive` scores local replays from their own score screens with the same scorer, and reports how often each signal fires.

### Hero statistics (YouTube title hooks)

`HeroStatsRefresh` (download role, and `heroesprofile hero-stats`) makes these calls for `YouTube:Titles:StatHooks` (issue #272; `docs/youtube-uploader.md`). Measured on 2026-10-08 with our key:

- Weekly allowances per endpoint (rolling 7 days, `x-hp-quota-limit` and `x-hp-quota-remaining`): `heroes/matchups` 100,000, `heroes/stats` 10,000, `heroes/maps` 10,000, `/patches` and `/heroes` 1,000,000. One refresh is `/patches`, `/heroes`, one `heroes/stats`, and about 90 `heroes/matchups`, once a day per game type.
- 60 requests a minute, polls included (`x-ratelimit-limit`). `group_by_map=true` is 1 a minute. The refresh spaces requests 1.1 s apart (`HeroesProfileApi:HeroStats:RequestSpacing`) and `group_by_map` calls 61 s apart (`GroupByMapSpacing`).
- A global call answers 202 `{"async":true,"status":"pending","job_id":"..."}` with `Retry-After` (10 s) and `x-global-job-id`. Polling `/jobs/{id}` costs no quota. The refresh waits `Retry-After` before each poll and gives up on a job after `JobTimeout` (15 min).
- 429 waits for `Retry-After` (60 s without one), at most 5 times. Its `HttpClient` (`heroes-profile-stats`) has no retry handler, unlike the replay calls above, so the refresh decides each wait itself. 401 or 403 (`endpoint_not_in_plan`, a bad key) stops the refresh until the download role restarts, with one warning. 422 (`timeframe_unavailable` early in a patch) skips that patch and game type until the next refresh is due. A 5xx or a network error is retried 3 times, 30 s apart. A hero whose matchups fail is saved without them.
- `enemy[].win_rate` in matchups is the queried hero's loss rate against that enemy (its `hovertext` says "Lost against a team with X"). Every rate is computed from `wins` and `games_played`, never read from `win_rate`.
- Heroes Profile's terms (section 4) require "Data provided by Heroes Profile" and a visible link to https://www.heroesprofile.com/ on the same screen as the data. The description's second line carries it whenever a hook is used.

All of these calls, and the player lookups below, go through one `HeroesProfileCaller` and one `HeroesProfilePacer` per process (#433), so together they keep the 60 a minute.

### Player records (focus-hero picks)

`PlayerHeroStatsFetch` (download role, and `heroesprofile player-hero`) asks for one player's Storm League record on one hero, for the focus picker's strength gate (#433: at least 20 games and 55% won). Measured on 2026-10-16 with our key (`Risllot#2619`, EU, Kael'thas: 27 wins of 54 games, KDA 6.12, MMR 2300, Silver 1):

- `players/heroes` allows 50,000 calls a week and 60 a minute; `players/privacy/changes` 10,080 a week. A cold `players/heroes` answers 202 with `Retry-After` 10 s and a job, collected from `/jobs/{id}` like a global call; the same query answered 200 at once afterwards. `players/heroes/single` returns the same record with every game type's MMR, about ten times the bytes, so it is not used.
- Errors carry `error.code`: 403 `player_unavailable` is a private profile, 404 `player_not_found` no such player, 422 `unknown_hero`, `unknown_region` or `unknown_game_type` a bad parameter. Each is kept for `HeroesProfileApi:PlayerStats:UnknownRetryAfter` (1 day). Any other 401 or 403 is the key or plan: lookups stop until a restart, with one warning.
- Answers are kept under `Data\HeroesProfile\players`, one file per player (region and a hash of the BattleTag): a record for `MaxAge` (7 days). Every call counts toward `WeeklyCallBudget` (15,000) in `calls.json`; past it, a record is unknown and the focus picker treats it so.
- Heroes Profile's terms require a cache of player data to read the privacy feed at least daily and drop whoever went private. `PlayerPrivacySync` reads it every `PrivacyInterval` (12 h) from the cursor in `privacy.json` (`since`, `after_id`; the first read only sets it, since nothing was cached before) and deletes each private player's file. On 2026-10-16 one day of changes was more than one page, so it follows `has_more` for up to 20 pages of 1,000 a pass.
- Focus videos never show a player's name or record, so this data needs no attribution line on YouTube.

### Targeted fetches (focus heroes the pool does not bring)

`FocusTargetedFetch` (download role, #433) fetches a game for a hero no focus has covered and no waiting replay has shown for `Focus:Targeted:After` (7 days). Measured on 2026-10-16 with our key:

- `/patches` names each patch's `season`: 34 for 2.57.0.98348, 33 for 2.57.0.98304 and 98285. Seasons 25 to 34 were valid; 35 and 40 answered 422 `invalid_parameters`. The fetch takes the newest season there.
- `/leaderboard?type=hero&hero=…&game_type=sl&season=…` allows 10,000 calls a week and 60 a minute, and answers 200 at once. Each row has `battletag`, `region_id`, `games_played` and `win_rate` (0 to 100).
  - One season shows few games: Murky's current board had 23 players, none with 20 games.
  - Six seasons merged (34 back to 29) had 203 players, and 35 of them had 20 or more games at 55% or more.
  - So the fetch merges `Focus:Targeted:Seasons` (6): games add up, and wins are each season's win rate times its games. The merged record is the strength bar (`Focus:MinHeroGames`, `MinWinRate`).
- `/players/matches?battletag=…&region=…&game_type=sl&hero=…&start_date=YYYY-MM-DD` allows 50,000 calls a week and 60 a minute. A cold query answers 202 with a job, like `players/heroes`.
  - Each row has `replayID`, `game_date` (UTC), `winner` (1 when the player won) and the full score line; there is no game version.
  - The fetch tries the player's won games first, best KDA first.
  - For each game, `/replay/{id}` (through the listing) gives the build. A game is downloaded only when it is Storm League, launchable by spectate's rules, and inside the focus media window (`ReplayMedia:FocusCandidateMaxAge`, 7 days; `Focus:Targeted:Lookback` is 6).
- **Limits.** The fetch makes at most one attempt per `Focus:Targeted:Interval` (2 h), stops while `MaxWaiting` (2) fetched replays wait, and counts its own calls against `WeeklyCallBudget` (2,000).
- **What it stores.** `Data\Focus\targeted.json` keeps hero attribute ids and replay ids only, never a player.

Auth is `Authorization: Bearer` ([Migrating](https://www.heroesprofile.com/Api/Migrating)). The v1 key is `op://Heroes Replay/Heroes Profile API Key/password` (skill `op-service-account`). The old `api.heroesprofile.com` `api_token` key is not accepted.

## Twitch extension

The spectator feeds the Heroes Profile Twitch extension while a replay is on screen, when `TwitchExtension:Enabled` is true. It is false in every appsettings file. That API is not part of the external v1 spec and is not in the Kiota client.

Base URL: `https://www.heroesprofile.com/api/twitch/v1/`  
Auth header: `X-HP-Twitch-Key` (an uploader key from https://www.heroesprofile.com/Api/Account). The v1 Bearer key is not accepted.

| Call | Path |
| --- | --- |
| Check the key | `GET uploader/whoami` |
| One full game so far | `POST uploader/snapshot` |

`heroesreplay check twitch-extension` calls whoami when the extension is enabled. The key URI is `op://Heroes Replay/Heroes Profile Twitch Uploader Key/password`, and `tools/fill-secrets-from-op.ps1` writes it once that item exists. Snapshots use phases `lobby`, `in_game`, and `ended`, paced by the match clock. The server applies `delay_seconds` from whoami before viewers see the update.

To check a key before turning the extension on, enable it for the check process only:

```powershell
$env:HEROES_REPLAY_TwitchExtension__Enabled = 'true'; heroesreplay check twitch-extension; Remove-Item Env:HEROES_REPLAY_TwitchExtension__Enabled
```

A rejected key fails with the server's message (HTTP 401: "This uploader key is not valid."). An accepted key passes and prints `entitlement.active`. Set `TwitchExtension:Enabled` true in `appsettings.prod.json` only after it prints `entitlement.active=True`.
